# Job-Based API Workflow

Several Sandbox APIs follow an **asynchronous, job-based workflow** to process requests that involve large input payloads or long-running computations.

Instead of sending the complete input directly in the API request, these APIs break execution into clearly defined steps that improve reliability, scalability, and performance.

In this workflow, you:

1. **Submit a JOB** to initialize processing  
2. **Upload the input payload** using a pre-signed URL  
3. **Poll the JOB** until processing completes and the output is ready

This guide walks you through the **entire JOB lifecycle** and explains how to implement each step consistently across Sandbox APIs.
## When to Use Job-Based APIs

Job-based APIs are used when:

- Input payloads are large (JSON, CSV, ZIP, etc.)
- Processing is compute-intensive or time-consuming
- Results cannot be generated synchronously within a single request

This model allows Sandbox to process requests asynchronously while giving you full control over input uploads and execution tracking.

---

## Job Lifecycle

Every request creates a **JOB** that moves through a well-defined set of states during its execution.

A JOB can have one of the following statuses:

- `created` — Job has been created and is ready to receive input
- `queued` — Job is waiting to be picked up for processing
- `in_progress` — Job is actively being processed
- `succeeded` — Job completed successfully and output is available
- `failed` — Job failed during processing

You can retrieve the current status of a JOB at any time by polling the job endpoint using the `job_id`.

## Step 1 — Submit the Job

The first step is to submit a **JOB** using a `POST` request.  
This initializes processing and returns the information required for the rest of the workflow.

Submitting a job provides:

- A **job_id** to track execution
- A **pre-signed S3 URL** to upload the input payload

---

### Endpoint Pattern
POST "/:workload/:function/:sub_function"

The **same endpoint** is reused later to poll the job status.  
Only the HTTP method changes (`POST` → `GET`).

---

### Example Response

```json
{
  "code": 200,
  "timestamp": 1765271144915,
  "data": {
    "id": "84f3844d-75ad-40a9-ab8d-73a7a4da7db2",
    "created_at": 1765271146287,
    "updated_at": 1765271146287,
    "@entity": "in.co.sandbox.<workload>.<function>.job",
    "url": "https://<signed-s3-upload-url>",
    "status": "created"
  },
  "transaction_id": "84f3844d-75ad-40a9-ab8d-73a7a4da7db2"
}
```

### Key Fields Explained

- `id`  
  Unique identifier for the JOB. This value is referred to as `job_id` and is required in later steps.

- `url`  
  An AWS S3 **pre-signed URL** used to upload the input payload in Step 2.

- `status`  
  Initial state of the JOB. At this stage, it will always be `created`.

---
Make sure to store the `job_id` securely. You will use it to upload the input payload and to poll the job status in subsequent steps.

---
## Step 2 — Upload the Input Payload (PUT)

After submitting the JOB, upload your input payload to the **pre-signed S3 URL** returned in Step 1.

This step uses a **plain HTTP `PUT` request** and does not interact with Sandbox APIs directly.

---

### Important Behavior

- The upload URL is an **AWS S3 pre-signed URL**
- It is **not** a Sandbox API endpoint
- The URL is valid only for a limited time
- Do **not** modify the URL in any way

---

### Request Requirements

- **Method:** `PUT`
- **Headers:**  
  - `Content-Type`
- **Body:**  
  - Input payload (JSON, CSV, ZIP, etc.)
- **Do NOT include:**  
  - Authorization headers  
  - Sandbox API keys  
  - Sandbox-specific headers  

---

### Example — Upload Using cURL

```bash
curl -X PUT \
  -H "Content-Type: application/json" \
  --data '@payload.json' \
  "https://signed-s3-upload-url"
```
A successful upload returns:

```text
200 OK
```
Once the payload is uploaded successfully, the JOB automatically moves to the next stage and begins processing.

---
## Step 3 — Poll the Job Status

After the input payload is uploaded, the JOB begins processing asynchronously.

To track progress and retrieve the final output, poll the **same endpoint used in Step 1**, but with a `GET` request and the `job_id`.

---

### Endpoint Pattern

```http
GET /:workload/:function/:sub_function/:job_id
### Example Response

```json
{
  "code": 200,
  "timestamp": 1765272159032,
  "data": {
    "id": "84f3844d-75ad-40a9-ab8d-73a7a4da7db2",
    "status": "in_progress",
    "created_at": 1765271146287,
    "updated_at": 1765272159032,
    "@entity": "in.co.sandbox.{workload}.{function}.job"
  }
}
``` 
### Example Response

```json
{
  "code": 200,
  "timestamp": 1765272159032,
  "data": {
    "id": "84f3844d-75ad-40a9-ab8d-73a7a4da7db2",
    "status": "in_progress",
    "created_at": 1765271146287,
    "updated_at": 1765272159032,
    "@entity": "in.co.sandbox.{workload}.{function}.job"
  }
}
```
### Job Status Handling

- `created`, `queued`, `in_progress`  
  Continue polling at regular intervals.

- `succeeded`  
  Output is ready and can be accessed using the downloadable URL.

- `failed`  
  Job execution failed; inspect the error details in the response.
  ### Successful Job Response

When the JOB succeeds, the response includes a **downloadable URL** for the output:

```json
{
  "code": 200,
  "data": {
    "id": "84f3844d-75ad-40a9-ab8d-73a7a4da7db2",
    "status": "succeeded",
    "output_url": "https://downloadable-output-url"
  }
}
```
Use the `output_url` to download the processed result.  
The URL is time-bound and will expire after a limited duration, so make sure to download and store the output as needed.
